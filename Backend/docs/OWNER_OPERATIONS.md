# Owner operations API

All requests require `Authorization: Bearer <Firebase ID token>`, an active owner profile, and ownership of the referenced shop. Responses use `{success:true,data:...,requestId}`; validation, ownership, and conflict failures use the existing error envelope. No SMS OTP is generated by these endpoints: Firebase Phone Authentication verifies the user before API access.

| Method and path | Request | `data` response |
| --- | --- | --- |
| `GET /v1/owner/car-washes/:id/services` | none | `{services:[{id,name,category,priceMinor,durationMinutes,active,...}]}` (all services, including inactive) |
| `GET /v1/owner/car-washes/:id/availability` | `?date=YYYY-MM-DD` | `{date,slots:[{startAt,endAt,capacity,bookedCount,availableCapacity,enabled}]}` |
| `PUT /v1/owner/car-washes/:id/availability/:date` | `{slots:[{startAt,endAt,capacity,enabled}]}` | `{date,slots}` with server-managed `bookedCount` |
| `POST /v1/owner/car-washes/:id/walk-ins` | See below | `{booking}`; 201 when created, 200 for idempotent replay |
| `GET /v1/owner/car-washes/:id/earnings` | `?date=YYYY-MM-DD` | `{earnings:{todayMinor,weekMinor,currency,completedToday,completedWeek}}` |

Walk-in body:

```json
{
  "customerName": "Guest customer",
  "vehicle": "MH12 AB1234",
  "serviceId": "actual-service-id",
  "date": "2026-09-30",
  "startAt": "10:00"
}
```

Use `Idempotency-Key` (1–128 letters, digits, underscores or hyphens). Retain the same key and body when retrying an uncertain request. Reusing the key with different data returns `409 IDEMPOTENCY_KEY_REUSED`. A walk-in requires an active shop/service and an enabled existing slot with sufficient capacity and duration. Creation reserves capacity in the same transaction as the accepted booking. It stores a guest snapshot without creating a Firebase account. Start and complete it through the existing owner booking status endpoint. Guest bookings do not produce customer inbox notifications.

Booking responses include `customer:{displayName,phoneNumber}`, `vehicle:{registrationNumber}` for walk-ins, and `source` (`app` or `walk_in`). Prices come from the service at creation, not from client input.

Availability replacement is transactional: reserved start/end times cannot be removed or changed, and capacity cannot drop below booked count. Empty slots may clear an unreserved day. Duplicate start times and nonboolean enabled flags are rejected. Disabling a reserved slot prevents new bookings while retaining existing bookings.

Earnings are completed booking value, **not collected payments, payouts, or settlement balances**. `todayMinor` covers completion timestamps on the requested day in Asia/Kolkata; `weekMinor` covers that day and the six preceding calendar days. Results use INR minor units. Deploy the new `carWashId/status/completedAt/priceMinor` Firestore index before using this query in production.

`GET /v1/admin/dashboard` also returns `weeklyBookings:[{date,bookings}]`, oldest to newest, for the last seven India calendar dates. These are scheduled booking counts across all statuses.

Firebase Hosting routes `/v1/**` to `api` in `asia-south1`; `/api/**` is an optional compatible prefix. The Admin SPA rewrite follows those API rewrites. Direct Cloud Functions URLs continue to accept `/v1` paths. No deployment is performed by changing these files.

The Postman collection includes the new owner requests. `npm test` in `Backend/functions` covers route auth, owner isolation, slot preservation, idempotent walk-ins, guest status transitions, earnings boundaries, and HTTP prefixes. Firebase emulator/device smoke tests remain necessary before release; automated tests use a transaction stub and do not exercise Firestore contention or real SMS delivery.

The aggregate index includes the summed price field following the [Firestore index guidance](https://firebase.google.com/docs/firestore/query-data/index-overview).
